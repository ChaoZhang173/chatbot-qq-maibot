## 当前怎样判断、怎样读取

1. Host 先做本地防抖、强制 @、空闲退避和频率判断；此处无需调用模型。当前 talk_value=1.0，频率门通常不会再抽掉已通过其他检查的批次。
2. 统一核心的 QQ 资格规则在本地计算：@、叫名字、回复机器人或兴趣关键词可获得资格；普通消息按稳定的每消息抽样、当前概率 0.7。资格不是必回承诺。目前还会在规划上下文、动作过滤和最终发送前检查，不能仅保留提示词判断。
3. planner 读取人设、对话历史、工具和状态，决定 stop、reply 或执行工具；replyer 再生成语言。成功回复后规划循环可能再次调用 planner 才停止。不是每条外部消息都必定调用两次，也不是回复后必定多一次。
4. 固定人设来自进程已加载的全局配置。动态人设版本、事实和状态来自统一核心 SQLite／检索；不是每轮都从磁盘重新读取一整个人设文件。qq_context 已有 90 秒缓存，但键包含 session、query、last_event、persona_version、context_revision，变化会失效。
5. 历史来自 Host 会话消息，配置目标约 20，当前为缓存稳定性保留约 2 倍窗口并补齐工具链；不能把“20”理解成严格最多 20 条。
6. 统一上下文已经压缩：事实最多 3 条、人物资料最多 2 项、表达／俚语各少量；普通聊天不默认带活动回执。插件先移除旧的自有上下文再注入新块，没有逐轮无限追加同一块。固定规则和即时内容仍混排。
7. 工具 schema 已经部分按需发现；尚未发现的工具，其名称和完整描述仍会进入延迟工具目录，存在继续压缩空间。

主要代码入口：`extensions/maibot_unified_core/{plugin,service,compact_context,store,commands,media}.py`；Host `src/maisaka/{chat_loop_service,reasoning_engine}.py`、`src/maisaka/runtime.py`、`src/services/memory_flow_service.py`。Host 的上游未修改部分不重复收录于公开仓库，可从 MaiBot 1.3.14 取得；补丁与 SHA256 清单见 `patches/`。

## 保留的 20 条刷新方案

当前使用 OpenAI 兼容的 DeepSeek Chat Completions。该接口无状态：第 1 次发送人设，不意味着第 2–20 次请求可以省略它而仍记得。即使客户端不重复读文件，只要同样的文本进入 messages，输入 token 不会因此减少；服务端前缀缓存能减少费用／计算，但命中的 token 仍会计入输入统计。

建议分成以下三层，按会话隔离：

| 内容 | 刷新方式 | 每轮请求如何携带 |
|---|---|---|
| 核心性格、权限边界、工具规则 | 配置／版本变化才重建 | 每次提供精简、稳定、顺序固定的前缀 |
| 低频背景、兴趣、可复用记忆摘要 | 约 20 条新的外部消息，兼顾时间上限 | 携带有预算的短快照，不反复拼接长原文 |
| 最新消息、回复资格、任务结果、权限、引用与发送状态 | 每轮即时读取／计算 | 每轮补入最新内容；不等待 20 条 |

“20 条”统计外部消息，排除机器人自己的分段发送、工具结果和内部轮询。缓存必须带 session、角色版本、授权范围版本及证据修订号；切换会话／对象、显式纠正、权限变更、已引用证据撤回或关键任务状态变化需要立即失效。人物事实不应无条件复用给下一个说话者。缓存失败回到已有实时路径，不使用过期权限做决策。

不默认增加每 20 条一次的摘要模型调用。优先复用已有摘要或本地结构化截取；若新增摘要，必须把摘要调用本身和后续上下文费用计入净收益。刷新频率不是保证缓存命中的开关，服务端缓存仍受前缀一致性、工具列表及服务策略影响。

## 候选方案与优先顺序

| 编号 | 方案 | 可行性与收益依据 | 必须保留的条件 |
|---|---|---|---|
| P0 | 补齐 token、缓存、模型任务和费用观测 | 高；先让改动可核验。当前费用为零容易误导 | 峰谷价格包含工作日／节假日，不能只填每日时间段；历史费用单独标注估算 |
| P1 | 成功终结回复后本地结束本轮 | 中高；167 次候选、18.65% token 上限，是最直接的省调用方向 | 真正发送成功、无待完成动作／工具／新消息，原子化检查；失败和未知发送结果不能当成功；复用 stop_after_execution 语义前核对队列 |
| P2 | 固定前缀稳定化＋20 条低频快照 | 高，但费用收益待测；减少重复组装并争取缓存 | 不省略核心人设，不延迟即时资格；授权范围隔离；版本失效；固定规则置于变化内容前 |
| P3 | 延迟工具目录改为短目录、完整说明按需展开 | 中高；单个样本目录 2,084 字符，schema 已有部分懒加载 | 保留可发现性、准确工具名／参数和限制；需要的工具调用可用；工具清单顺序稳定 |
| P4 | 人物事实写回按证据去重、合并分段回复 | 中高；744 次／24h 与 277 次回复生成之间值得核实 | 基于证据修订／逻辑回复去重，不能只按人物加长冷却；纠正、删除和新事实必须及时处理；固定抽取规则前置 |
| P5 | 本地资格提前过滤“完全没有可行动内容”的轮次 | 中；可减少进入 planner 的无效轮次 | 无合格聊天不代表无任务；命令、@、任务回执、主动活动、跟进工具需要独立放行；不得重新随机抽样改变资格 |
| P6 | planner 与 replyer 分配不同上下文预算 | 中；planner 主要判断动作，可能不需完整表达资料 | 保留理解指代、人物和安全边界所需内容；必须回放判断一致性，不能让 planner 成为机械开关 |
| P7 | expression.selector 跳过／复用无新证据的选择 | 中；占 8.11% token，统计中无缓存命中 | 当前插件已为表达选择压缩上下文，额外收益不能重复算；保留多样性，不固定复用不合语境的表达 |
| P8 | 调整历史窗口，先做 20→30 等小范围回放 | 中低优先；缩短历史可能降低输入，但破坏前缀缓存 | 完整 tool-call/result 成对、保留未完任务与引用；不要一刀切移除图片；质量和缓存费用一起比较 |

不优先做：全面降低回复长度（输出只占约 2.5%）、只调 max_tokens（上限不等于实际输出）、把所有背景每 20 条才发送一次、把所有记忆写回加长定时、先换小模型承担整个决策链。现有证据也不支持归因于失败重试风暴。

## 如何验证再上线

第一阶段用脱敏／合成回放，不调用生产模型、不发真实消息：检查新消息竞争、分段发送、工具链、失败发送、跨群权限、人物纠正和缓存失效。P1 必须证明不会吞掉用户新消息和未完任务；P2 必须证明新说话者不会收到旧说话者的资料。

后续若实施在线小流量验证，每次只启用一个可回退开关，固定模型和观察口径；比较每 100 条外部消息的调用数、输入／输出 token、缓存命中与未命中、估算费用、漏回／误回、重复动作、事实更新延迟及回复风格。以真实费用与质量为主，token 总数为辅；重叠方案的收益不能直接相加。实施与部署另行执行，不把本次评审当作上线完成。
