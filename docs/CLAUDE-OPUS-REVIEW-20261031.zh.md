## 阅读原文前的复核修正

下面保留 Claude 的原始评审；其中有几处表述不能直接作为工程保证。最终采用 [合并后的优化方案](TOKEN-OPTIMIZATION-20261031.zh.md)。

1. **缓存 hit/miss 已经入库**，不是“只需入库”：`host/src/llm_models/utils.py:261-262` 已写入这两个字段，实际 7 天和 24 小时统计也来自这些记录。P0 的工作是补费用配置、峰谷日历和逻辑回合／证据关联，而非重建已有 token 统计。
2. **13.51% 费用占比已按候选调用实际 hit/miss 回算**，不是按平均命中率分摊：167 次候选合计 hit 945,152、miss 709,790、输出 3,340，估算 ¥0.74205304；同窗总费用估算 ¥5.49073406。仍是按当前价回算的候选上限，不是可兑现节省或平台账单。
3. **“尾部必然／每次都缓存未命中”“前移就能节省”过于绝对**：前缀发生变化会阻断其后的前缀复用，但实际命中还取决于重复请求、服务端缓存策略和请求序列。前移不稳定块也可能降低整体命中，必须按真实 hit/miss 做对照。
4. **“按证据 ID 去重不会丢失事实”不能保证**：消息可编辑、撤回，同一 ID 的内容和授权状态可变化；抽取失败、空结果、规则版本变化或第一次漏抽也需处理。应包含人物、授权范围、证据内容与修订、抽取版本，并仅在成功完成后记录去重状态；回放比较事实更新质量。不能假定删除必然产生新消息 ID。
5. **20 条外部消息不等于 Host 的 20 个历史项**：Host 还计入工具和内部消息；与裁剪协调是可测的设计选项，不能直接假定同步。即时权限、纠正和任务状态不等待裁剪。
6. **P1 不能仅因私聊就放宽批次条件**：私聊也会有多条消息和未完任务。即便只有一次成功 reply，也可能只是承诺后续查找；需要可验证的终结条件、批次末尾检查和正常的新消息唤醒机制。

认可并保留的重点：P4 优先；P1 在批次末尾限定范围；P2 拆开即时资格和稳定规则；P3 与前缀实验一起评估；P5 需要 Host 入口改动；P6/P7/P8 暂缓。模型对“每天几元是否值得优化”的价值判断不代替用户偏好，实施目标仍是兼顾费用与质量。

## 一、总体判断

1. 方案方向基本正确，对“接口无状态、缓存命中仍计输入 token、各项节省不能相加”的表述准确。但有三处需要修正：
   - **最有价值的结构性问题方案没有点明**：统一核心上下文块、延迟工具目录、当前时间、注意事项和最终提醒都**追加在历史之后**，所以每次 planner 请求这部分必然缓存未命中（见第三节）。“20 条刷新”真正能节省 API 费用，靠的是“冻结并前移”这一条路径，而不是少读本地数据。
   - **P1 不能直接复用 `stop_after_execution`**：这个标志按工具设置，在整批工具执行完后生效。如果在 `reply` 结果上无条件设置，会吞掉同批其他工具的结果，也会吞掉同批第二条合格消息。需要在批次末尾做条件判断（见第四节）。
   - **P4 的重复来源在代码中已经可以确认**：Host 每发送成功一个分段就触发一次人物事实写回，而各分段的用户证据几乎相同。可以按证据去重，比按人物冷却更安全。
2. 量级提醒【统计】：按方案回算，24 小时费用约 ¥5.49，P1 候选上限约 ¥0.74/天。绝对金额很小，所以**质量回归的代价远高于节省额**。优先级应该偏向“低风险、可回退、可观测”，而不是追求最大的节省比例。
3. 不应对外宣称任何具体的节省百分比。文档中的 18.65%、13.51% 都是上限或估算（理由见第七节）。

## 二、20 条刷新思路

### 2.1 哪些可行，哪些只省本地 I/O

- 【代码】`qq_context` 的缓存键为 `(session_id, query, last_event_id, persona_version, context_revision)`，TTL 为 90 秒（`repo/extensions/maibot_unified_core/service.py:674-684`）。query 和 last_event 每来一条新消息都会变，所以**实际上每条新消息都会重建**：包括记忆检索（含 embedding）、`native_learning_context` 和 `native_profile_context`。
- 如果只是“每 20 条重新检索一次、其余复用”，**节省的是本地 SQLite/检索 I/O 和少量 embedding 调用**【统计】（7 天 embedding 共 347,150 token，可以忽略）。只要同样的文本仍然进入 messages，**LLM 输入 token 不会减少**。
- 真正能节省 API 费用的前提是：低频块**字节级稳定**，并且**放在会变化的历史之前**，这样服务端前缀缓存才能命中。命中的 token 仍计入 `prompt_tokens`，但按缓存命中价计费。因此观测上必须分开记录 hit 和 miss 两列。Host 已经在逐请求获取这两项（`host/src/maisaka/chat_loop_service.py:1314-1323`），P0 只需要把它们入库。

### 2.2 当前块放在哪里（关键）

- 【代码】插件先移除旧的上下文块，再把新块 `append` 到 items **末尾**（`plugin.py:82-91`）。Host 本身已经把注入消息、当前时间、尾部消息、注意事项和最终提醒都排在历史之后（`chat_loop_service.py:1091-1116`），延迟工具目录也属于注入消息（`reasoning_engine.py:255`）。
- 【代码】历史裁剪带滞后：超过 2N 时裁到 N（`host/src/maisaka/context/post_processor.py:15-16, 53-59`）；选择窗口同样是 2N（`chat_loop_service.py:94, 1422-1426`）。所以在两次裁剪之间，“系统段 + 历史”这段前缀是稳定且可缓存的；而**尾部那几千字符每次都未命中**。同一轮内 round 2 重新请求时，round 1 的输出和工具结果被插在尾部之前，尾部依然未命中。
- 【推测】因此，“固定规则 + 低频背景”从尾部移到系统段之后、历史之前，是 P2/P3 的主要收益来源。前提是这块内容在两次刷新之间保持完全不变；否则每变一次就会让后面整段历史的缓存失效，反而更差。

### 2.3 建议的分层（修订）

| 层 | 内容 | 失效条件 | 位置 |
|---|---|---|---|
| L0 稳定 | 核心人设、`CONTEXT_RULE`/`content_rules.RULE`/`receipts.RULE`、工具使用说明（`service.py:698, 703-705`）、精简工具目录 | 配置或人设版本变化、策略重载 | 系统段之后，顺序固定 |
| L1 低频 | 动态人设快照（`compact_context.persona`）、群级表达和俚语、低频兴趣摘要 | 约 20 条外部消息**或**时间上限；`persona_version`、`context_revision`、授权或策略版本变化时立即失效 | 紧跟 L0、在历史之前 |
| L2 即时 | 资格表、当前说话者资料证据、按 query 检索到的事实、回执和活动、权限复核、时间 | 每轮 | 维持在尾部 |

要点：
- **必须先拆开 `rule` 字符串**【代码】：`qq_reply_policy_context` 会把**逐条消息的资格 JSON** 拼进 `rule`（`service.py:444-450, 699`）。所以现在的“固定规则”其实混入了即时内容，不能整体前移。`commands.context`、`media.context` 是否逐轮变化，本次未核实，前移前需要审计。
- **按 query 检索的事实和说话者资料不能冻结 20 条**：它们依赖当前消息和说话者（`service.py:669, 710-729`）。冻结后会把旧说话者的资料带给新说话者，这一风险方案已经指出。真正适合低频刷新的内容其实很少，主要是动态人设和群级表达。
- **刷新时机建议与历史裁剪对齐**【推测】：历史大约每 N（≈20）条计数消息裁剪一次，裁剪本身就会让历史缓存失效。如果 L1 恰好在裁剪时刷新，每个周期只损失一次缓存，正好对应用户提出的“约 20 条”。如果刷新计数独立于裁剪，每个周期会多损失一次。
- 计数口径：在 `ingest_qq` 中累计已接收的外部消息，排除机器人自身、notify 和 command，以及工具结果和分段发送。计数器放在进程内存，按会话隔离，重启即重建（重建只是多刷新一次，不影响正确性）。
- 撤回与授权：权限必须每轮复核（现有 `service.py:668, 692` 两次检查要保留）。纠正或删除记忆需要确认会调用 `context_revision` 的递增（`store.py:238`），本次**未核实**所有删除和纠正路径是否都会触发；未覆盖的路径需要补上。
- 不新增“每 20 条一次的摘要模型调用”。这一点同意方案。

## 三、P1：成功回复后本地结束

### 3.1 现状【代码】

- 内层循环：`reasoning_engine.py:879-916`。round>0 时会先**无条件接入**期间到达的新消息（`:881`），再请求 planner。
- 工具批次末尾：如果有工具 `success and stop_after_execution`，就在整批执行完后 `_enter_stop_state` 并结束（`:2062-2063, 2075-2085`）。
- `reply` 成功时**没有设置** `stop_after_execution`（`builtin_tool/reply.py:702-715`）。多段发送时，只要某段失败就 `break` 并返回失败（`:641-651, 673-685`），前面已发出的分段不会回滚。
- 失败的 reply 会继续下一轮（`reasoning_engine.py:2059-2060`）。
- 聚焦模式另有一条路径（`focus/group_runtime.py:701`）。

### 3.2 直接复用会吞掉什么

1. **同批的其他工具**：如果模型在一批里同时调用了 `reply` 和查询类工具（联网、记忆、图库），而 `reply` 带有停止标志，整批执行完就停，查询结果不会再被 planner 看到。
2. **同批第二条合格消息**：例如一批中有 A、B 两条合格消息，round 1 只回复了 A，原本 round 2 会去处理 B。插件的资格表把已回复的消息标为 claim（`service.py:449, 469`），但 Host 看不到这些资格信息。
3. **回复期间到达、但动态门控未放行的消息**【代码】：新消息到达时会走调度器（`runtime.py:1007-1009`，`scheduler.py:32-62`），可能被延迟或拒绝（`:98-104`）。现状下它们会在 round 2 被无条件接入（`:881`）；如果直接停止，它们要等下一条消息才会被处理。
4. **“稍等，我查一下”式的承诺**：回复里承诺了后续动作，原本下一轮会去执行。
5. 主动或内部任务的多步流程，以及 wait 挂起的状态。
6. 空闲退避的语义：`tool_stop_after_execution` 属于空闲原因（`mode_policy.py:4-7`，`idle_backoff.py:41-53`）。现状是回复轮记为 `tool_continue`（重置退避），下一轮 stop 再记一次空闲；改动后只记一次空闲，净计数相同，但监控上难以区分。建议使用独立的结束原因（例如 `reply_completed`），并显式决定它是否计入退避。

### 3.3 最小可行范围

不要在 `reply.py` 里设置标志。应在 `_handle_tool_calls` 的批次末尾（`reasoning_engine.py:2075` 之前），当以下条件**全部**满足时才走现有的停止路径：

1. 本批工具调用只包含 `reply`（可另带 `send_emoji`），而且全部 `success`。`success` 已经意味着所有分段都发送成功。
2. 非聚焦模式、非主动或内部任务触发的轮次，且没有挂起的 wait（`_has_pending_wait_tool_call()`）。
3. 判断时刻 `not runtime._has_pending_messages()`（`runtime.py:1581`）。如果有待处理消息，就按现状继续。
4. 第一阶段只限于**本轮来源批次只有 1 条外部、非命令消息，且 reply 的目标正是这条消息**；或者私聊。第二阶段再由插件提供“本批未 claim 的合格消息数 = 0”的判定（需要新增 Host 查询接口或 hook）。
5. 设一个配置开关，默认关闭；使用独立的结束原因并入库。

这个范围会明显小于 167 次候选上限，具体覆盖多少需要数据（第八节）。

## 四、P3 / P4 / P5：重复与真实省调用

### P3 延迟工具目录：**修改后保留**
- 【代码】`build_deferred_tools_reminder` 为每个未发现的工具输出“名称: 完整 description”（`runtime.py:1490-1518`）。完整 schema 已经是 tool_search 发现后才暴露（`:1417-1428`，`reasoning_engine.py:215-256`），这部分优化已经存在，方案所说“部分懒加载”属实。
- 不会少一次模型调用，只会缩短未命中的尾部。更大的收益来自**位置**：目录在未发现集合不变时是稳定的，前移到历史之前即可命中缓存。缩短描述的风险是可发现性下降，需要比较 tool_search 次数和工具误用率。

### P4 人物事实写回：**保留，建议提前**
- 【代码】在 send_service 路径中，每发送成功一个分段就调用一次 `on_message_sent`，然后把消息加入写回队列（`send_service.py:916-920` → `memory_flow_service.py:1012-1016`）。`reply` 是逐段调用发送的（`reply.py:630-640`）。另有 `uni_message_sender.py:321-326` 也会触发，同一条消息是否会经过两条路径，本次**未确认**。
- 【代码】证据取自“该时间点之前最近 6 条同人用户消息”（`memory_flow_service.py:251-288`）。同一回复的各分段相隔几秒，证据集合几乎相同。提示词明确要求事实**只能来自用户原话**，机器人回复只作参考（`:402-409`）。
- 结论：按 `(person_id, sorted(evidence_message_ids))` 在短 TTL 内去重，**不会丢失事实**（证据不变，就没有新的事实来源）。用户纠正或删除会带来新的消息 ID，因此不会被误去重。这确实能**少一次模型调用**，并且纯本地、可回退。
- 现有过滤只有“≤8 字符且含客套词”（`:482-500`），比较弱。也可以加上“目标证据全部已经提取过就跳过”。`_parse_fact_items` 已经对单次返回去重（`:446-454`），但不能跨调用去重。
- 732/744 次只输出 1 token【统计】，很可能是 `[]`。【推测】它说明绝大多数写回调用没有产出，这与分段重复触发吻合。但这需要读取正文才能确认。

### P5 本地资格前置过滤：**修改，需要 Host 补丁**
- 【代码】资格判断已经在本地按消息完成（`service.py:412-432`），并且在 planner 输出和最终发送前都会强制检查（`:452-503`）。但调度器**不读取**插件资格（`scheduler.py:64-105`），所以全部不合格的批次仍会调用 planner，planner 再根据资格表自行 stop。这是**真实的、可以省掉的整次调用**。
- 【代码】`maisaka.planner.before_request` 的 `allow_abort=False`（`chat_loop_service.py:234-236`），插件无法在这里中止请求。要实现，必须给 Host 加补丁（在调度器或回合开始时询问插件），或者新增一个可中止的 hook。
- 必须放行的情况：@ 或强制触发、命令、回执请求、wait 超时、主动任务、私聊、`owner_command_queue` 等。需要注意的是，不合格的批次里 planner 仍可能做非回复动作（例如 `gallery_save`、学习）。这部分比例未知，需要数据。
- 不得重新抽样：资格结果已经按消息持久化（`:423, 429`），直接读取即可。

## 五、planner 与 replyer 拆分（P6）：**暂缓，仅做小幅调整**

- 【代码】两者使用同一份 `qq_context`（`plugin.py:97-105`）；`expression_selector` 已经单独精简（`:84-87`）。
- planner 需要资格表、权限和规则；它写出的 `reply_reference` 决定回复方向，因此仍然需要事实和人物资料来理解指代，以及判断“该不该接”。如果从 planner 中移除事实，可能造成方向偏差，而 replyer 无法纠正方向。
- 可以从 planner 移除的只有表达和俚语（每类最多 2 条，每条 ≤100 字符，`compact_context.py:27-28`），收益很小。在 2.3 的重排完成之前，不值得为此单独承担风险。
- 角色表现主要由 replyer 承担，replyer 侧不应删减。

| P7 表达选择 | **暂缓，先查原因** | 方案中“统计中无缓存命中”意味着可能是提示词顺序问题（可变内容在前），本次未核实；先改顺序，比跳过调用风险更低 |
| P8 历史窗口 | **暂缓** | 当前已有 2N→N 的滞后裁剪，有利于缓存；缩短窗口会改变裁剪周期和质量 |

## 七、统计与费用口径问题

1. **18.65% 是 token 份额，不是费用份额**：回复后的 stop 轮与 round 1 共享“系统段 + 历史”前缀，只有尾部和新增项未命中。【推测】它的缓存命中率应明显高于平均值，实际费用节省会低于 token 比例。13.51% 的费用估算需要确认是否**逐请求**使用了 hit/miss 价格，而不是用平均命中率摊算。
2. **167 次只是上限**：还没有扣除同批多条合格消息、回复中的承诺、并发消息和主动任务。
3. **planner 占 62% 包含缓存命中部分**：按 token 排序会高估 planner 的费用占比，高估程度取决于它的命中率（未知）。
4. **744 与 277 不能直接相除得出重复倍数**：写回由所有成功发送的消息触发，包括主动发送和插件发送，不只是回复。
5. **各方案不能相加**：P1、P2、P3 都会作用在同一批 planner 请求上；P2 改变前缀后，P1 省下的那次请求本身也会变便宜。
6. 字符数不等于 token 数；6 份请求样本不具代表性。这两点方案已说明，同意。

## 八、建议先做的三项

1. **P0 观测**：逐请求入库 `prompt_cache_hit/miss_tokens`、`request_type`、`cycle_end.reason`、写回调用的输出长度和证据 ID 集合，以及费用按 hit/miss 分价计算。不改变任何行为，零风险。
2. **P4 写回证据去重**：在 `PersonFactWritebackService._handle_message` 中，于 `_extract_facts` 之前按 `(person_id, evidence_ids)` 加 TTL 去重。纯本地实现，有开关，失败时回到原路径。
3. **P1 窄版本**：按 3.3 节的条件 1–5 实现，默认关闭，先在离线回放中验证。

随后作为第一个**实验**（而非直接上线）：P2+P3 前缀重排。先拆出 `rule` 中的即时内容，再在小流量上比较 hit/miss 和回复质量。前移规则可能削弱它们的“近因”约束力，建议在尾部保留一句很短的提醒。

## 九、验证与回退条件

- **P1 回放用例**：回复期间到达新消息（包括门控拒绝和 @）；同批两条合格消息；`reply` 与查询工具同批；分段部分发送失败；带承诺的回复；主动任务；wait 挂起；聚焦模式。通过标准：新消息全部被后续回合处理；与基线相比没有漏回，也没有重复回复。
- **P4**：同一回复多分段时只提取一次；用户在下一条消息中纠正时仍会提取；对比写回事实的集合，在回放中与基线一致。
- **P2**：说话者切换后不得带出旧说话者的资料；`persona_version`、`context_revision`、权限变化后立即刷新；同一刷新周期内低频块的字节哈希保持一致（入库哈希即可验证）。
- **线上回退条件**（每次只开一个开关）：每 100 条外部消息的漏回或误回上升、出现重复回复、事实更新延迟超出阈值、出现跨会话或跨说话者的资料泄露（一次即回退），或者 miss token 不降反升。

## 十、需要额外数据才能确定的结论

1. reply 之后的下一轮分布：stop、再次 reply、调用工具、wait 各占多少。以及 167 次中来源批次只有单条消息的比例（决定 P1 窄版本的覆盖面）。
2. 每类请求的 hit/miss token（尤其是 planner round 2 与 round 1 的对比，以及 expression.selector）。
3. 写回调用的正文：`[]` 的比例；同一 `reply_id` 的分段触发次数；`uni_message_sender` 路径是否与 send_service 重复触发。
4. 全部不合格的批次进入 planner 的次数，以及其中 planner 做出非 stop 动作的比例（决定 P5 是否值得打 Host 补丁）。
5. 所有记忆删除和纠正路径是否都会递增 `context_revision`。
6. `commands.context`、`media.context` 的内容是否逐轮变化。
7. DeepSeek 前缀缓存在本业务请求长度下的实际命中粒度和保留时长（官方说明为尽力命中）。

## 总结

方案方向正确，但需要修改的地方比文档写得更具体。最有价值的发现是：统一核心块、工具目录等尾部内容每次都缓存未命中。所以“20 条刷新”只有做到“拆出即时内容、冻结低频内容、移到历史之前、与历史裁剪同步刷新”，才会节省 API 费用；否则只省本地 I/O。

P1 不能在 reply 上直接设置 `stop_after_execution`，应在批次末尾按严格条件判断，第一阶段只覆盖单消息批次。

P4 的分段重复触发已由代码确认，可以按证据去重，安全且能真正省调用。

P5 能省调用，但需要 Host 补丁和更多数据。P6/P7/P8 暂缓。

建议先做 P0、P4、窄版 P1，再把前缀重排作为对照实验。总费用约为每天 ¥5 的量级，质量回归的代价高于任何节省。
